## 1. Схема БД

Три таблицы в PostgreSQL 16, создаются миграцией Alembic.

| Таблица | Поля |
|---|---|
| `users` | `id` (int, PK), `email` (unique), `password_hash`, `created_at` |
| `notes` | `id` (uuid, PK), `user_id` → `users.id` (ON DELETE CASCADE), `title` (≤120), `text`, `created_at`, `updated_at` |
| `audio_records` | `id` (uuid, PK), `note_id` → `notes.id` (ON DELETE CASCADE), `file_path`, `duration_sec`, `size_bytes`, `created_at` |

Подробное описание и код для dbdiagram.io: [db-schema.md](db-schema.md).

## 2. Запуск через Docker

Проект запускается одной командой `docker compose up --build`. В `docker-compose.yml` два сервиса: `db` (PostgreSQL 16 с проверкой готовности `pg_isready`) и `api` (FastAPI). `api` стартует только после того, как база стала healthy, при старте сам применяет миграции, а данные БД и аудиофайлы хранятся в именованных томах `pgdata` и `audio`, поэтому переживают перезапуск.

Ошибки и решения: исходный `docker-compose.yml` не запускался, потому что внутри `services:` был вложен второй `services:`, — вынесли сервисы и тома на верхний уровень. В `requirements.txt` оказался `pip freeze` из другого проекта без FastAPI, — заменили на список прямых зависимостей и после первого запуска зафиксировали версии. Контейнер `api` не мог стартовать без настроенного Alembic, — выполнили `alembic init` внутри контейнера и взяли адрес базы из переменной окружения.

## 3. Аутентификация

Использовали JWT-токены (библиотека PyJWT) и хеширование паролей bcrypt. При регистрации пароль не сохраняется: в базу записывается только bcrypt-хеш со случайной «солью», поэтому даже одинаковые пароли дают разные хеши, а по хешу пароль восстановить нельзя. При входе сервер берёт хеш из базы и проверяет им введённый пароль; если всё верно, выдаёт токен, подписанный секретным ключом из `.env` (алгоритм HS256). В токене записан id пользователя и срок действия 60 минут. Клиент отправляет токен в каждом запросе в заголовке `Authorization: Bearer <токен>`. Сервер проверяет подпись и срок: если токена нет, он подделан или просрочен, ответ 401. Такой подход не требует хранить сессии на сервере, а в Swagger работает кнопка Authorize.

[СКРИНШОТ: Postman, `POST /auth/login`, статус 200 и `access_token` в ответе]

## 4. CRUD

| Операция | Метод и адрес | Код ответа |
|---|---|---|
| Создать заметку | `POST /notes` | 201 |
| Список своих заметок | `GET /notes` | 200 |
| Получить заметку с аудио | `GET /notes/{id}` | 200 |
| Изменить заметку | `PUT /notes/{id}` | 200 |
| Удалить заметку и её аудио | `DELETE /notes/{id}` | 204 |
| Загрузить аудио (M4A) | `POST /notes/{id}/audio` | 201 |
| Скачать аудио | `GET /audio/{id}` | 200 |
| Удалить аудио | `DELETE /audio/{id}` | 204 |

Ошибки: 401 без токена, 404 чужой или несуществующий объект, 413 файл больше 20 МБ, 415 не M4A, 422 неверные данные (пустой заголовок, длительность больше 600 секунд).

[СКРИНШОТ: Postman, `POST /notes` с телом запроса и ответом 201]

## 5. Связи между данными

У пользователя много заметок (один ко многим), у заметки много аудиозаписей (один ко многим). Связи сделаны внешними ключами с каскадным удалением: удалили пользователя — удалились его заметки, удалили заметку — удалились её аудиозаписи. Сами аудиофайлы лежат на диске в Docker-томе, в БД хранится только путь к файлу и метаданные, поэтому файлы при удалении заметки или записи удаляет код сервера. Пользователь видит только свои данные: все запросы фильтруются по владельцу, на чужую заметку сервер отвечает 404, как будто её нет.

## 7. Что исправили после замечаний

Код проверили ревьюером и автотестами (50 тестов pytest на отдельной тестовой базе). По итогам доработали:
- пароль длиннее 72 байт (например, из русских букв) ронял сервер с ошибкой 500, потому что новая версия bcrypt не принимает такие пароли — теперь регистрация отвечает 422, вход 401;
- заголовок из одних пробелов принимался — теперь пробелы по краям обрезаются и такой заголовок даёт 422;
- слишком большой файл сервер сначала принимал целиком и только потом отказывал — теперь запрос отклоняется сразу по заголовку `Content-Length`;
- при обрыве загрузки на диске мог остаться «осиротевший» файл — теперь он удаляется;
- две одновременные регистрации с одним email давали 500 — теперь 409;
- при удалении заметки удаляется и её папка с аудио;
- зафиксировали версии зависимостей, чтобы обновление библиотек не меняло поведение незаметно.

Полный список ошибок: [errors.md](errors.md).

## 8. Вывод

Серверная часть готова: регистрация и вход по JWT, CRUD заметок, загрузка и скачивание аудио с ограничениями по формату, размеру и длительности, изоляция данных пользователей; всё запускается через Docker Compose и покрыто автотестами. Я разобрался, как устроены миграции Alembic, хеширование паролей, JWT-токены и почему чужой объект лучше отдавать как 404.
